# Dynamic Memory for DeepSeek Harness

Durable long-term memory for a Harness agent: it keeps an evidence layer, user and assistant portraits, a calibrated retriever, and a small cognition layer (consolidation drafts, recompute, disclosure policy). It only adds what is missing from the context window; it does not re-inject the current conversation.

- **Evidence first**: observations are separated into `observed / self_reported / inferred / corrected`. Inferred claims need a confidence and at least one alternative explanation. User corrections always win; contradictions are kept, not silently merged.
- **No fixed personality taxonomy**: the plugin stores guesses with sources and confidence, not labels. Portrait facets are configurable (`facets`, `assistantFacets`); nothing forces “introvert/extrovert” style buckets.
- **Language-neutral core**: all runtime text comes from locale packs (`locale/messages.*.json`); word lists, disclosure defaults and facet labels are data, not code. Chinese is a supported locale, not a hard dependency.
- **Time-aware**: observation scope (transient/situational/durable) is derived on read; TTL only stops injection, it never deletes. Inferred confidence decays from the last corroboration.
- **Disclosure policy**: `proactive / if_asked / never`; sensitive or transient items default to `if_asked` and are marked “tone only” in context.
- **Safe by default**: delete cascades to references, dispose awaits in-flight writes before closing storage, capture can be paused.

## Install (Preview)

This is a Cordis **bundle plugin** for DeepSeek Harness, not a standalone app.

1. Clone the repository.
2. Install the repository path as a bundle into your Harness profile (plugin manager `install_bundle`).
3. Reload, then run `/dmem stats`; `storage: durable` confirms persistence. Data lives in `$DSH_HOME/storages/dynamic_memory/`.

Release channels: Preview (`main` + tags) → installable bundle → Stable (npm later; `package.json` is currently `private: true`). **2.5.2 is a test version** (tag pushed; 2.5.2 is docs-only); **npm not pushed**, not Latest; the GitHub Release page was not verified here.

## Cost and fit (v2.0.3)

- The tool description shrank from ~7.3KB to ~0.5KB; automatic injection only appears when there is content, and identity continuity is off by default.
- Extractive summaries are generated by default for cross-session overview; portraits/observations are still written by the model, so an empty store stays empty.
- If you only need to "look things up now and then", official session search + `notes.md` is cheaper; this plugin fits cross-session continuity, correctable portraits and evidence chains.
- `private` observations are masked in tool output unless `includePrivate: true`.

## v2.1 Index-only capture (done)

Positioning: **Harness sessions are the only source of plaintext; the plugin stores a local derived index.** It is not an encryption product and has no cloud sync.

- **Stored**: summary, keywords, entities, time, `textHash` (SHA-256, verification only), `pointer` (sessionId + time). New rows keep `user`/`assistant` as empty strings (`retainText: false` is the default).
- **Not stored**: plaintext copies of user/assistant turns; no application-level encryption or passphrase (privacy relies on full-disk encryption and file permissions). Existing rows were already stripped: 2120 rows, ~2.9M characters freed.
- **Reading the original text**: a search hit is hydrated by reading the local Harness session via its pointer — pairing by `textHash`, then summary prefix, then a unique time-window candidate; snippets by default, full turns with `full=true`.
- **Current state (real-machine spot check)**: hydration **19/20 = 95%**. The one failure is explicit and never fabricated: a repeated "继续"-style prompt whose row cannot be uniquely located among 54 candidates in its session — `sourceAvailable: false`, empty text, `hydrationError: no matching user message (54 candidates)`; a no-match, not ambiguous, not an unreadable session. Summary/keywords/entities still match in retrieval.
- **Rollback (limited)**: `memory.md` is exported automatically before stripping, but it is a **readable archive** (portraits, observations, 30 latest impressions with at most 80 chars of user text), not a byte-exact backup of all 2120 rows. For a literal restore use a pre-strip storage snapshot (copy `$DSH_HOME/storages/dynamic_memory/`); `/dmem export` likewise stays at summary level.
- Migration is available both as a tool action and as `/dmem migrate mode=strip confirm=true` (shared implementation; exports memory.md first, refuses without `confirm=true`; destructive).

## Consent switches (v2.2, C1-C4)

- `consent.memory / inject / profile / sensitive` persist in the storage `consent` table and survive reloads; verified on a real machine: **`memory=on inject=on profile=unified sensitive=off, storage=durable`**.
- `/dmem consent` prints status; `/dmem consent on|off` (C1), `inject on|off` (C2), `sensitive on|off` (C4), `profile unified|situational|off` (C3); the tool action also accepts `consent={memory,inject,profile,sensitive}`.
- C1 off: no capture, no injection, background indexing stops; since v2.2.1 `memory=off` also rejects explicit writes (`observe`/`learn`/`deepen`/`correct`), and the consent row carries `schemaVersion=1`.
- **Still not done**: speaker attribution (`speaker`/`origin` isolation), situational portrait grouping, no real dsh-go device test (static checks only). Multi-agent memory isolation shipped in v2.5.0 and was hardened in v2.5.1 (next section).

## Multi-agent memory isolation (v2.5.0, hardened in v2.5.1)

Teammates/subagents **cannot read or write** owner memory by default; one agent's memory never leaks into another's.

- **`memoryScope`**: `owner` (default; only root agents use owner memory, delegated agents inject nothing and their writes are refused), `agent` (each `agentId` gets its own namespace; root agents still see pre-upgrade rows), `shared` (legacy profile-wide behaviour).
- **Identity resolution priority**: `config.ownerAgentIds` > session header (`parentSession` / `origin=subagent` / `delegationDepth>0`) > `agents.roots()` vs `list()`. An unprovable identity is **unknown and fails closed** (no read, no write); since v2.5.1 a bare header no longer proves owner.
- **Portrait primary key is `scopeId`** (`owner` or `agent:<agentId>`), never a session id; every exchange/observation/portrait carries it (old rows count as owner).
- **Archive ≠ delete**: `archive` only archives exchanges, the portrait stays active; only a deleted session marks its portraits `dormant` (never injected; visible via `stats.dormantFacets` and `/dmem scope`), and owner portraits are never touched.
- **`/dmem scope`** shows mode, identity source, namespace, read/write rights, whether the session inventory is verified, and dormant portraits; **`/dmem gc`** is dry-run by default; **with an unverified inventory nothing is marked dormant and nothing is deleted** (`reason=unverified-inventory`, even with `confirm=true`).
- **Verified**: `scope=owner`, `identity source=agents-roots`, `canRead/canWrite=true`, `dormantFacets=0`, inventory verified; gc dry-run deleted nothing.
- **Honest limits**: Harness has **no independent persistent agentId** (same human in a new session cannot be re-identified); a deleted session can only be marked dormant (**no persistent tombstone**; new sessions do not inherit old portraits); concurrent `agents.roots()` / `listSessions()` timing was **not verified on a real machine**. Tests 52 + 269.

## Isolation GC safety (v2.5.1)

- `gcRequireInventory: true` (default): without a complete `listSessions()` array nothing is marked dormant and `/dmem gc` only reports (`reason=unverified-inventory`) — even `confirm=true` deletes nothing.
- On old Harness builds with no delegation header and no `ownerAgentIds`, identity stays unknown: read/write/injection are refused and never fall back to owner.

## Panels: Web and dsh-go app

**Why the phone needs its own surface**: dsh-go is a Flutter-native UI and does **not** execute Web client plugins; the v2.3.0 `client.js` is Web/desktop only, so the app needs its own `dshGo` manifest + declarative view.

- **Web / desktop (v2.3.0)**: `client.js` adds a memory panel on the input dock (`conversation.input.dock`) — status, search, portraits, pause/resume, C1–C4 switches, export. Every read/write goes through `/dmem`; destructive actions only show the `/dmem migrate` hint. Confirmed with live client inspect: slot occupant `id=dynamic-memory, order=30, active=true`.
- **dsh-go app (v2.4.0)**: `package.json` gains `main: index.js` and `dshGo` (`v=1`; panel `memory-settings`, placement `session.tab` / `features` / `chat.panel`, presentation page; bilingual title; icon settings; `wants: []`; `minApp` omitted). `index.js` registers via `ctx.inject(['dshGo'])`; on desktop/Web without the service it does not run.
- **Where to find it in the app**: conversation details → "Plugins" → "Memory settings"; "All features" → "Memory settings"; composer "plugins" capsule → sheet.
- **Panel content**: storage health (storage / index rows / plaintextRows / last injected chars), **four C1–C4 toggles**, and **five buttons (pause capture, resume capture, export, copy status, consent note)**; every registered action is reachable.
- **Write path**: toggles only emit `/dmem consent …` — memory → `/dmem consent on|off`, inject → `/dmem consent inject on|off`, sensitive → `/dmem consent sensitive on|off`, profile cycles `unified → situational → off`; nothing writes storage directly, so the app, tool and Web panel share one persistence path. **No new network requests**; no clipboard/input reads (`wants: []`).
- **Install/activate**: manifest changes are re-read automatically; `index.js` changes need an engine restart from the app's "Engine" page. If the bridge only scans `$DSH_HOME/dsh-go/plugins/`, an extra `dsh plugin --profile web add <pkg dir>` is required (discovery rule **unconfirmed**).
- **Uninstall/rollback**: `dsh plugin --profile web remove @local/dynamic-memory`, then delete the package directory; memory data under `$DSH_HOME/storages/dynamic_memory/` is untouched. Panel rollback = reinstall 2.3.0, or drop the `dshGo` manifest (entry disappears, data stays).
- **Not tested on device**: this machine has **no dsh-go device and no kit `check.mjs`**, so rendering, taps and state-after-reload were **not tested in the app** — the only dsh-go check is `node ui/verify-dshgo.mjs` static 46 PASS + 1 INFO (the sole dsh-go verification, including rendered-action reachability), and tests (currently 52/269) contain **no dsh-go assertions** (`grep dshGo test*.mjs` = 0). The three interfaces (dual identity, discovery rule, `scope.sessionId`) remain unconfirmed.

## Evaluation (real store, local; re-run at v2.5.2)

- `node eval.mjs`: hit@3 **9/10**, MRR **0.750** (after eval-label migration; 7/10, 0.600 before labels were migrated);
- `node eval.mjs --min-coverage 0.6`: false positives **0/8** (1/8 without the gate);
- `node eval.mjs --fixture`: **5/5** (MRR 1.000);
- One genuine remaining loss: a deployment-style query — the 90+60-char summary cut drops key tokens (a coverage gap; see the evaluation report).
- **Scope caveat**: the real set has only 10 positives / 8 negatives and is **not a frozen test set**; these numbers are a local regression baseline, not a generalisation claim.

## Known limits

- No embeddings: synonym paraphrases can still miss; retrieval is lexical (CJK bigrams + word scripts + entities).
- Identity continuity is evidence, not authentication.
- Consolidation drafts require ≥3 distinct sessions; a sparse store will produce none.
- Chinese is fully reviewed; English/other locales are functional (prompts, labels, word lists, tokenizer fallback) but need native-speaker polish.
- The evaluation set is small (10 positives / 8 negatives) and not frozen: 9/10, MRR 0.750 are a local regression baseline only.
